# 03 · The pipeline

The pipeline turns stored source files into the data each page draws. It has one job beyond that: stop when a source does not add up, so a wrong number never reaches a page.

## Why it is shaped this way

The site must open by double-clicking a file, with no server and no network. That one requirement decides most of the design:

- Pages cannot `fetch()` JSON from `file://`. So the build writes each page's data as a script that sets one global: `window.DATA = {...};`. The page loads it with a plain `<script>` tag.
- No modules, no bundler, no package manager for the site. Each page has one script. The chart library is a single vendored file.
- The data bundles are tracked in git, so the site works for someone who never runs the build.
- All arithmetic happens in Python, where it is tested. The page formats and draws.

## Repository layout

```text
build.py                  runs everything; --fetch downloads new files first
pipeline/
  fetch.py                download what is missing, record where it came from
  parse_<source>.py       one raw file -> one plain dict, checked against itself
  derive_<study>.py       parsed dicts -> one JSON-ready dict per page
data/
  raw/<source>/           files exactly as published, plus sources.json
  assumptions.json        hand-edited inputs of the chain study
  processed/              dumps of every parsed table, for inspection (git-ignored)
site/
  index.html ...          one HTML file per study
  <page>.js               one script per page
  <page>-data.js          written by build.py; tracked in git
  styles.css  ui.js       shared by every page
  vendor/                 chart library and world map
tests/
index.html                redirect to site/, for static hosting
.nojekyll
docs/brief.md
```

Name pages, data keys and source folders in the site's language. Keep Python identifiers and docstrings in English.

## The flow

```text
fetch (optional) -> parse each raw file -> derive per page -> write bundles
                         |                      |
                    stops on a            stops on a
                    failed check          failed check
```

`build.py` runs the four steps in order. If any parser or derive step raises, it prints the file and the failed check and exits with a non-zero status. **It writes nothing in that case**: all writing happens after every check has passed.

The bundle writer is five lines. Use it as is:

```python
def _write_js(path: Path, name: str, data: dict) -> None:
    path.write_text(
        f"// Generated by build.py. Do not edit by hand.\nwindow.{name} = "
        + json.dumps(data, ensure_ascii=False)
        + ";\n"
    )
```

Each bundle carries a `generated` date. The page prints it in the footer.

On success the build prints one line per bundle with what it covers (how many files, first and last period) and then every warning.

## Raw files are evidence

- A file under `data/raw/` is stored exactly as published. Nothing edits it and nothing overwrites it. If the publisher re-issues a file, the new one is stored beside the old one.
- Each folder has a `sources.json` that maps file name to the URL it came from. The page links both: the stored copy and the publisher.
- `fetch.py` reads the publisher's listing page, downloads only the files not yet on disk, and records each URL. For an API, it saves each raw answer as one file per year or query and never asks again for a year it already has. To refresh a year, delete its file.
- Respect the source's limits. Sleep between calls when the API asks for it. If an answer has exactly as many rows as the API's cap, treat it as cut off and stop.
- Use a generic user agent. Put no personal details in requests.

> **Wool example.** Ten monthly PDFs, twenty-eight annual PDFs, and one JSON answer per calendar year from the UN Comtrade public API (one call per second, 500 rows per call). Two of the monthly PDFs are corrected re-issues. When an original and its re-issue are both on disk, the later issue date wins and the page lists the file it replaced.

## What a parser guarantees

One parser per source format. Its whole interface is one function: a path in, a plain dictionary out. Whatever the format (PDF, spreadsheet, CSV, API answer), it keeps these promises:

1. **Identity.** The result says which file it is, when it was issued, and which period it covers. If the file does not say, the parser raises.
2. **Blank is absent, never zero.** An empty cell produces no key. A period the report has not reached yet is dropped.
3. **Printed shares and averages are not read.** They are recomputed downstream from quantities and money. Sources misprint them.
4. **Every table is checked against its own printed totals** before the function returns: rows against row totals, columns against column totals, and tables against each other where they report the same total.
5. **Tolerance comes from rounding, not from convenience.** If each printed value is rounded to 0.1, a sum of *n* values may drift by 0.05 × *n*. Allow that and no more.
6. **Unknown things fail loudly.** A country, port, product, month label or table layout the parser does not know raises an error that names the file, the table and what to add. Nothing is skipped silently.
7. **Names are canonical.** The parser maps each printed label to one fixed key. The mapping tables live in the parser and are the single place to extend.
8. **Tables are found by their headers, not by position.** Layouts drift between issues: a spacer column appears, a label column is duplicated, a header is garbled. Locate a table by the first word of its header row and a column by its header name.

Two levels of strictness, chosen per source:

- For the current source, any disagreement stops the build.
- For old files of the long-run source, a disagreement *within* a table still stops the build, but a disagreement *between* two tables of the same file is collected as a warning. The period stays usable and the page lists the warning.

The parser's docstring states these guarantees and any decision a reader would not guess.

## What a derive step decides

One derive function per page. It takes parser output and returns one JSON-ready dictionary. Its docstring opens with "what it decides, so the page doesn't". The reference site's derive steps decide these, and yours will decide the same kinds of things:

- **Which version of a period to use.** The latest file that prints it. Earlier versions are kept in a `revisions` list.
- **Which months are provisional.** A month of an open period that has appeared in fewer than a fixed number of issues.
- **How to get per-month detail from cumulative reports.** Subtract each report's period-to-date total from the next one's. A difference can be negative where a report revised earlier months down; keep it, do not clip it.
- **Like-for-like comparisons.** The current period to date against the same months of the previous one.
- **Every share, average and unit price**, from quantities and money.
- **Periods are consecutive.** A gap raises.
- **Method eras.** Each period carries a flag for the method its source used, and series that do not survive a method change are given per era.
- **One-off distortions.** If one month books a year of adjustments, the step computes the affected figures with and without it.
- **Joins across studies.** The opportunities step takes the outputs of the other derive steps and adds only the arithmetic that joins them. It raises if a band does not add up to its total.

Blank stays absent through the derive step. Nothing missing becomes zero.

## The assumptions file

The chain study rests on inputs no statistical source gives: a shelf price, a weight, losses, price lists, duty rates, company margins. They live in one hand-edited JSON file. The build validates it before using it.

```json
{
  "_note": "Inputs of the chain page. Dates read: YYYY-MM-DD.",
  "product": {
    "name": "<brand and product name>",
    "url": "https://…",
    "read": "YYYY-MM-DD",
    "composition": "<as printed>",
    "quote": "<the exact line from the product page>"
  },
  "parameters": {
    "shelf_price": {
      "name": "List price in the brand's own shop",
      "value": 95.0,
      "unit": "USD",
      "type": "source",
      "reread": true,
      "source": "<site and page>",
      "url": "https://…",
      "date": "YYYY-MM-DD",
      "note": "Without sales tax. Sale prices seen the same day: …"
    },
    "unit_weight_g": {
      "name": "Weight of one unit",
      "value": 133,
      "min": 102,
      "max": 146,
      "unit": "g",
      "type": "source",
      "reread": false,
      "source": "<retailer page of the previous model>",
      "url": "https://…",
      "date": "YYYY-MM-DD",
      "note": "The brand does not publish it. Minimum: …. Maximum: …."
    }
  },
  "comparables": [
    {
      "stage": "<stage>",
      "company": "<listed company, segment>",
      "year": "2025",
      "gross": null,
      "operating": 0.01,
      "note": "<what the segment includes and what was not checked>",
      "url": "https://…",
      "reread": false
    }
  ]
}
```

Every parameter has a `type`:

| Type | Meaning |
| --- | --- |
| `computed` | The build computes it from the main source. |
| `source` | A published figure. |
| `inference` | Your own calculation from published figures. |
| `assumption` | No direct source. |

`reread` is true only if the figure was read again at the original page while the site was being built. A figure a search step reported and nobody opened is `false`. The page shows this column.

The loader stops the build when:

- a parameter has an unknown type;
- a parameter that is not an `assumption` lacks `source` or `url`;
- a parameter has a range and its value is outside it;
- a comparable lacks `url` or a true-or-false `reread`.

## How the chain is computed

Per one unit of the product:

1. **Mass balance, backwards.** Product weight → the intermediate bought by the last stage (plus its loss) → the one before, back to the place's export product.
2. **Raw material.** The export product at the main source's price for the latest complete period.
3. **Stage ladder.** Each stage buys what the previous one sold. Value added is sale minus purchase. The build raises if a stage sells for less than it buys.
4. **Border.** Duty on the customs value, plus freight per unit.
5. **Brand and shop.** Shelf price minus landed cost.
6. **Cost and profit.** A stage's profit is a listed company's operating margin times the stage's sales. Cost is value added minus that profit.
7. **Scenarios.** The same ladder, re-run with one input changed. The ranges printed on the page are the minimum and maximum across scenarios, computed here.

Anchor the factory price on a published cost breakdown for a comparable product if one exists; component price lists give a floor, and asking prices for finished goods a ceiling. Say on the page which is which.

## Tests

Tests run on the real stored files. They are the record of every way the sources have misbehaved.

- **Every stored file parses**, and the set has one issue per period.
- **Known values.** A handful of figures copied by hand from the source, asserted exactly.
- **One test per awkward layout.** When a file needs a repair, the repair gets a test, and the test module's docstring lists which file has which quirk.
- **Blank is not zero**, asserted on a real blank cell.
- **Number formats**, including the malformed ones that must raise.
- **Unknown names raise.**
- **A re-issue replaces the earlier file.**
- **Derived totals close.** Per-month differences of a period sum to its latest period-to-date total.
- **The chain closes.** Mass balance, each stage buys what the previous sold, value added sums to the shelf price, ranges bracket the base case.
- **The loader refuses bad assumptions**, tested with a copy that lacks a source.
- **Joins stop on bad input.** A band that does not add up, or a source row that straddles two bands, raises.

Derive tests that need no real file use a small hand-made input. Mark any test that takes two seconds or more as `slow` so a quick run can skip it.

## Tooling

- Python 3.12 or later, run through `uv`. One runtime dependency: the library that reads the source format (a PDF table reader, a spreadsheet reader, or none for CSV and JSON). Development: `pytest` and `ruff`.
- Commands, to put in the project README:

```bash
uv run --frozen python build.py --fetch
```

```bash
uv run --frozen pytest -q
```

```bash
uv run --frozen ruff check .
```

- `.gitignore` excludes `data/processed/`. It does not exclude the bundles.
- Round derived figures to a fixed number of decimals before writing. Otherwise each build rewrites the bundles with noise in the last digits, and git shows a change where there is none. (The reference site has this wart.)

## Publishing

Any static host works. For GitHub Pages serving the main branch: a root `index.html` with a meta refresh to `site/index.html`, so the pages' links to `../data/raw/` keep working, and an empty `.nojekyll` so the host serves the files untouched.
